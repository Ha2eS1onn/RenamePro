# 文档转换测试方法

本文档说明怎么验证 RenamePro 的文档转换功能（`docx → pdf`、`pptx → pdf`、`md → docx` 等）。
分三条路径，按需要选：

| 方式 | 适合 | 命令 |
| --- | --- | --- |
| A. 一键自动校验 | 想快速知道"到底正不正常" | `verify-docengine.ps1`（三种模式，见「二」） |
| B. 手工验证 | 想亲眼看进度框、亲手点托盘 | 见「三、手工步骤」 |
| C. 内置自检 | 改完代码后回归 | `RenamePro.exe --selftest` |

> 三种引擎来源分别对应三种测法：**真实引擎直连**（`-Soffice`）、**随包引擎目录**（`-EngineDir`）、
> **发布包目录包**（`-Package`，最接近用户拿到的形态）。

---

## 一、准备：真实文档引擎

功能测试必须用**真实 LibreOffice**：内置自检里手搓的最小 docx 会被真实引擎拒收，
只能验流程、验不了功能。

```powershell
# 下载官方 MSI（349 MB）并解包到 D:\RenamePro-dev\libreoffice（不安装、不注册 COM）
powershell -ExecutionPolicy Bypass -File .\setup-lo-dev.ps1
```

脚本会校验官方 SHA256，最后跑一次 `soffice.com --version` 作为探针。
如果网络很慢，可以用分段并行下载（实测 12 段能把 0.06 MB/s 拉到 4.7 MB/s）：

```powershell
powershell -ExecutionPolicy Bypass -File .\obj\lo-engine\dl-lo-msi.ps1 -Segments 12
# 下好后把它交给 setup 脚本解包：
powershell -ExecutionPolicy Bypass -File .\setup-lo-dev.ps1 -MsiPath 'D:\RenamePro-dev\msi\LibreOffice_25.8.7_Win_x86-64.msi'
```

引擎产物在 `D:\RenamePro-dev\libreoffice\`（仓库外，不入库，随时可删）。

**随包引擎目录**（发布用途）由 `build-docengine.ps1` 从上面那棵树裁剪而来：

```powershell
# 完整裁剪（每裁一类跑一次矩阵冒烟，失败自动回滚，约 10~20 分钟）
powershell -ExecutionPolicy Bypass -File .\build-docengine.ps1
# 已有裁剪好的 obj\lo-payload\stage 时复用（省十几分钟，只做清理/清单/复制）
powershell -ExecutionPolicy Bypass -File .\build-docengine.ps1 -ReuseStage
```

产物在仓库的 `libreoffice\`（约 703 MB / 4547 个文件）：结构和官方安装一致（`program\`、`share\`、
`licenses\`、`payload.json`），发布时由 `publish.ps1 -Mode Docs` 复制成包内的 `LibreOffice\`。
Debug 构建会自动把它复制到输出目录，所以 `dotnet build -c Debug` 之后直接跑自检就能验它。

## 二、方式 A：一键自动校验（`verify-docengine.ps1`）

### 模式 1：真实引擎直连（开发回归）

```powershell
dotnet build RenamePro.csproj -c Release
powershell -ExecutionPolicy Bypass -File .\verify-docengine.ps1 `
  -Soffice 'D:\RenamePro-dev\libreoffice\program\soffice.com' -KeepRunning
```

通过 `RENAMEPRO_SOFFICE` 把程序指到那棵树，验的是"转换质量"。

### 模式 2：随包引擎目录（验裁剪树）

```powershell
powershell -ExecutionPolicy Bypass -File .\verify-docengine.ps1 -EngineDir .\libreoffice
```

把 `RENAMEPRO_DOCENGINE` 指向裁剪后的目录、并把 `documentEngine` 设成 `bundled`，
所以**只可能**用这棵树：既能验"裁剪没裁坏"，也顺带验了新的引擎发现路径。

### 模式 3：发布包目录包（最接近用户形态）

```powershell
powershell -ExecutionPolicy Bypass -File .\publish.ps1 -Mode Docs
powershell -ExecutionPolicy Bypass -File .\verify-docengine.ps1 -Package .\dist\RenamePro-全功能版-v1.2.0.zip
```

解压发布包到 `obj\dist-pkg\`，用包里的 `RenamePro.exe` + 同级 `LibreOffice\` 跑完整矩阵，
断言：

- 托盘日志里的引擎来源是「随包目录」；
- `%RENAMEPRO_DOCROOT%\runtime` 下**没有** `doc-*` 目录（随包目录版不该再解压任何载荷）；
- 产物 magic、副本、只读位、跨族拒绝等 15 条用例全部符合预期。

三种模式都会：生成真实夹具（`obj\verify-fixtures\`，含中文标题、表格、图片、多页 PPT、
多工作表、Markdown、HTML）→ 写测试用 `config.json` → 启动托盘程序 → 逐个改名 →
断言产物 magic 与日志结果 → 打印 PASS/FAIL 表并给出退出码。

覆盖的用例：

| 类型 | 用例 | 期望 |
| --- | --- | --- |
| 成功 | `report.docx → report.pdf` | OK，产物 `%PDF-`，副本生成 |
| 成功 | `slides.pptx → slides.pdf` | OK |
| 成功 | `sheet.xlsx → sheet.pdf` | OK |
| 成功 | `sheet.xlsx → sheet.csv` | OK，首工作表导出 |
| 成功 | `report.docx → report.odt` | OK，PK + mimetype |
| 成功 | `report.odt → report.docx` | OK（覆盖导入侧过滤器） |
| 成功 | `report.docx → report.html` | OK |
| 成功 | `page.html → page.pdf` | OK |
| 成功 | `notes.md → notes.docx` | OK（**内置转换器，不需要引擎**） |
| 失败 | `report.docx → report.xlsx` | SKIPPED，原因提到 csv/pdf |
| 失败 | PNG 改名成 `.docx` | SKIPPED，原因 `不在文档集合内` |
| 失败 | pptx 内容装成 `.docx` | SKIPPED，原因 `magic 不符` |
| 边界 | 只读文件 | OK，只读位恢复，无残留工作目录 |
| 边界 | 中文 + 空格文件名 | OK |
| 回归 | `photo.jpg → photo.png` | OK，产物是真 PNG |

`-KeepRunning` 会保留托盘程序，测完你可以自己去 `obj\verify-fixtures\case-*\` 打开产物人工检查。

## 三、方式 B：手工步骤

1. **准备发布包**：解压 `dist\RenamePro-全功能版-v1.2.0.zip`，目录里应当是
   `RenamePro.exe` + `LibreOffice\` + `使用说明.txt`（`LibreOffice\` 约 703 MB）。
2. **启动**：双击 `RenamePro.exe` → 托盘出现图标（无窗口、无控制台）。
3. **准备文件**：任意一个 `.docx`（例如 `报告.docx`）放进一个空目录（例如 `D:\demo\`）。
4. **改名**：在资源管理器里把 `报告.docx` 改成 `报告.pdf`。
5. **看现象**：
   - 若开启了 `showProgressDialog`，会弹出资源管理器同款进度框；
   - 目录里出现 `报告 - 副本.docx`（原格式副本）与 `报告.pdf`；
   - 打开 PDF：中文不乱码、表格有框线、图片在、页数合理。
6. **看日志**：`config.json` 同级目录的 `log.txt`，应当有这四类行：

```
[INFO] [文档] 引擎就绪：LibreOffice 25.8.7.3（D:\demo\RenamePro-全功能版\LibreOffice\program\soffice.com，随包目录）
[INFO] [入队] 正在转换 报告.docx → 报告.pdf | 通道: Document
[INFO] [文档] 转换完成（文字处理 转换（.docx → .pdf），产物 42.3 KB）
[INFO] [结果] OK | 旧: D:\demo\报告.docx | 新: D:\demo\报告.pdf | 副本: D:\demo\报告 - 副本.docx | 耗时: 2.1s
```

7. **反向验证**（确认"不会乱转"）：
   - 把 `a.docx` 改成 `a.xlsx` → 预期 `SKIPPED`，原因里提到"跨族只允许 pdf（表格请改成 csv/pdf）"；
   - 把一张 PNG 改名成 `伪装.docx` → 预期 `SKIPPED`，原因 `不在文档集合内`（源扩展名不在管线）；
   - 把 `slides.pptx` 改名成 `fake.docx` → 预期 `SKIPPED`，原因 `magic 不符：内容实为 ooxml-presentation`；
   - 先用 Word 打开 `b.docx` 再改名 → 预期 `FAILED` 并给出文件被占用的原因（这是预期行为，不是缺陷）。
8. **托盘菜单**：右键图标 → 「文档引擎：…」显示当前引擎与来源（随包目录 / 系统安装 / Office COM /
   环境变量覆盖）。v1.2 起没有"立即解压文档引擎"这一项——引擎就是普通目录，没有解压这一步。
9. **故意把 exe 单独复制走**（只复制 `RenamePro.exe`，不带 `LibreOffice\`）：预期文档转换降级为
   "找系统 LibreOffice / Office COM"，找不到时写一条警告并跳过改文档名——图片与音视频不受影响。
10. **图片/音视频回归**：`photo.jpg → photo.png`、`clip.mkv → clip.mp4` 各来一次，
    确认文档功能不影响它们，也确认第一次音视频转换会解压内置 FFmpeg（约 150 ms）。

## 四、方式 C：内置自检与桩引擎校验

```powershell
# 内置自检：格式嗅探、转换矩阵、内置 Markdown 转换器、随包引擎目录、端到端
& .\bin\Release\net8.0-windows10.0.19041.0\win-x64\RenamePro.exe --selftest; $LASTEXITCODE
# 结果同时写进 selftest-report.txt，退出码 0 = 全绿
#   没有随包引擎目录时第 4 节是 [SKIP]，其余全绿同样算通过
#   Debug 构建（bin\Debug\…）会自动带上 libreoffice\ → 第 4 节会实测随包引擎

# 桩引擎校验：不用真实 LibreOffice，验的是"集成链路"（参数拼接、产物找回、原子替换、降级）
powershell -ExecutionPolicy Bypass -File .\test\stub-engine\build-stub.ps1
powershell -ExecutionPolicy Bypass -File .\verify-docengine.ps1 -Soffice .\test\stub-engine\dist\soffice.com
```

分工：`--selftest` 验代码逻辑，桩引擎 + `verify-docengine.ps1 -Soffice` 验进程与文件交互，
`-EngineDir` / `-Package` 验真实引擎与发布形态。

> 自检里的"残留引擎进程"只统计**本次自检启动之后**才出现的 `soffice` / `soffice.bin`，
> 并会给 15 秒宽限期等它们退出：机器上本来就常驻的 LibreOffice（或快速启动）不会被误判为残留。

## 五、测试时重点看什么

1. **产物本身**：中文有没有掉字形、表格线、图片、页数、公式结果——这是 LibreOffice 方案最真实的验收点。
2. **日志的四类行**：`[文档] 引擎就绪`（**括号里的来源要对**）/ `[入队] … 通道: Document` /
   `[结果] OK` / 失败时的 `原因:` 是否具体可操作。
3. **首次转换的额外耗时**：第一次会创建 LibreOffice 用户配置目录
   （`%LOCALAPPDATA%\RenamePro\DocEngine\profile-*`），比后续慢几秒（托盘启动时的后台预热通常已经做过）。
   若日志出现 `[文档] 首选配置目录不可写…改用…`，说明走了 `%TEMP%` 兜底——功能不受影响，但值得知道。
4. **有没有残留**：目录里不该留下 `.renamepro-doc-*` 工作目录；`Get-Process soffice*` 不应有残留进程。
5. **没有"解压"痕迹**：v1.2 起全功能版不嵌入文档引擎，因此 `log.txt` 里不该出现
   `文档引擎载荷已解压`，`%LOCALAPPDATA%\RenamePro\runtime` 下也不该出现 `doc-*`。

## 六、已知限制（别误判为缺陷）

- **Office COM 路由在本机测不了**：环境导致 Word/Excel 自动化失败（PowerPoint 可用），因此联调走 LibreOffice 路由。
- `md → docx` 走**内置转换器**，与引擎无关；它可用不代表引擎可用，反之亦然。
- 跨族转换（`docx → xlsx`）按设计拒绝，不是 bug。
- `.txt` 不在文档管线内（无 magic 可校验，且 txt 改名是高频误操作）。
- PDF 作源默认关闭（`allowPdfSource: false`），开启后也只保证文字内容。
- 真实 LibreOffice 与 Microsoft Word 的分页可能不同，属正常差异。
- 随包引擎目录若被用户改成"只读"或被安全软件隔离，引擎自检会失败并降级到系统引擎 / Office COM；
  日志会写明路径与原因。程序目录本身也需要可写（`config.json`、`log.txt` 就写在同级）。

## 七、清理

```powershell
Remove-Item .\obj\verify-fixtures -Recurse -Force          # 夹具与产物
Remove-Item .\obj\dist-pkg -Recurse -Force                 # -Package 模式解压出来的发布包
Remove-Item .\obj\doc-work -Recurse -Force                 # 测试用的 profile 与工作根
Remove-Item D:\RenamePro-dev -Recurse -Force               # 引擎与 MSI（要重测就留着）
Remove-Item .\libreoffice -Recurse -Force                  # 随包引擎目录（发布前别删）
Remove-Item "$env:LOCALAPPDATA\RenamePro" -Recurse -Force  # 运行期缓存与 LibreOffice profile
```
